Roadmap: WhatsApp DM to Event Carousel

Build a system where a user sends an event by WhatsApp DM, your bot parses it with A/B logic (simple parser vs LLM), posts the validated event to a WhatsApp Group, and displays event slides in a browser carousel running on Raspberry Pi devices.

Core StackNode.js + Baileys + Docker Compose
AB TestPath A: rule parser / Path B: LLM API
DisplayWeb carousel + optional kiosk mode
TargetLocal dev first, Raspberry Pi deployment next

Execution Plan

Phase 0 - Foundation & Architecture

Week 1

Define boundaries, folders, contracts, and local orchestration.

Deliverables

  • Monorepo structure: bot, api, display, shared.
  • docker-compose.yml for local full stack.
  • Event schema: title, start/end, location, notes, source metadata.

Success Criteria

  • All services start with one command.
  • Health checks are exposed and visible in logs.

Phase 1 - WhatsApp Bot Ingestion (Baileys)

Week 1-2

Implement DM message intake and normalize into parse requests.

Deliverables

  • Baileys connection lifecycle (auth persistence + reconnect behavior).
  • DM-only command path and sender allow-list option.
  • Raw message capture with idempotency key.

Notes

  • Reference: https://baileys.wiki/docs/intro/.
  • Persist auth/session on named volume for restart safety.

Phase 2 - Parsing A/B Test Engine

Week 2

Route each parse request to a parser variant and compare output quality.

Variant A (Simple Parser)

  • Regex + date normalization + fallback defaults.
  • Confidence score from required field coverage.

Variant B (LLM API)

  • Prompt with strict JSON schema and examples.
  • Retry with guardrails if malformed response.

Experimentation

  • Split strategy: random 50/50 or sender-sticky assignment.
  • Track latency, parse validity, human correction rate.

Phase 3 - Validation, Storage, and Group Publishing

Week 2-3

Validate event payloads, store canonical events, and publish to WhatsApp Group.

Deliverables

  • Validation pipeline with user feedback loop on invalid fields.
  • Persistent DB (SQLite for local, Postgres optional for growth).
  • Formatted group announcement template.

Success Criteria

  • New valid event appears in DB and group chat.
  • Duplicate DM does not create duplicate events.

Phase 4 - Carousel Display Service

Week 3

Build a lightweight web UI to show upcoming events on one or many devices.

Deliverables

  • Auto-refresh event API polling or websocket updates.
  • Carousel with duration, transition, and fallback states.
  • Responsive kiosk-friendly mode for TV/Pi displays.

Success Criteria

  • Same display URL works on local and remote Pi devices.
  • Updated events appear without manual browser refresh.

Phase 5 - Raspberry Pi Hardening & Operations

Week 4

Ensure reproducible deployment on ARM devices and stable runtime behavior.

Deliverables

  • Multi-arch images (amd64 + arm64) or Pi-native builds.
  • Compose profile for low-resource mode.
  • Backup strategy for auth data + event database.

Observability

  • Structured logs with request ids across services.
  • Basic dashboard: parse success, AB distribution, bot uptime.

Key Risks & Mitigations

  • WhatsApp session invalidation - keep auth state volume-backed and alert on reconnect loops.
  • LLM cost/latency spikes - gate with fallback to parser A and enforce token limits.
  • Date parsing ambiguity - send confirmation DM when confidence is below threshold.
  • Pi resource constraints - keep display app static-first and trim container base images.
